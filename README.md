# 🐾 PetCostTrack

**ระบบบันทึกและคำนวณค่าใช้จ่ายแฝงของคนเลี้ยงสัตว์**
Web Application สำหรับบันทึก จัดหมวดหมู่ และสรุปภาพรวมค่าใช้จ่ายในการเลี้ยงสัตว์เลี้ยง — ทั้งค่าใช้จ่ายหลักที่วางแผนไว้แล้ว และ **"ค่าใช้จ่ายแฝง"** ที่มักถูกมองข้าม พร้อมระบบแชร์ข้อมูลให้สมาชิกในครอบครัวที่ร่วมดูแลสัตว์เลี้ยงตัวเดียวกันเห็นภาพเดียวกัน

## ที่มาและปัญหา

ปัจจุบันการเลี้ยงสัตว์เลี้ยงในสังคมเมืองของไทยมีแนวโน้มเพิ่มขึ้นต่อเนื่อง โดยเฉพาะในกลุ่มคนวัยทำงานและครอบครัวรุ่นใหม่ที่มองสัตว์เลี้ยงเป็นสมาชิกในครอบครัว ผู้เลี้ยงส่วนใหญ่มักวางแผนงบประมาณเฉพาะค่าใช้จ่ายที่มองเห็นชัด เช่น ค่าอาหาร ค่าฉีดวัคซีน แต่ในความเป็นจริงยังมี **ค่าใช้จ่ายแฝง** อีกจำนวนมากที่เกิดขึ้นไม่สม่ำเสมอและมักถูกมองข้าม เช่น ค่ารักษาพยาบาลฉุกเฉิน ค่าซ่อมแซมข้าวของที่สัตว์เลี้ยงทำเสียหาย หรือค่าฝากเลี้ยง

ปัญหาหลักที่พบจากการวิเคราะห์กระบวนการทำงานปัจจุบันของผู้เลี้ยงสัตว์ มี 4 ข้อ:

1. **ไม่มีเครื่องมือบันทึกค่าใช้จ่ายที่ไม่ได้วางแผนไว้อย่างเป็นระบบ** — ทำให้ประเมินต้นทุนที่แท้จริงของการเลี้ยงสัตว์ต่ำกว่าความเป็นจริง
2. **ข้อมูลค่าใช้จ่ายกระจัดกระจายหลายช่องทาง** — เงินสด แอปธนาคาร แชท สมุดจด ไม่มีศูนย์กลางข้อมูลเดียว
3. **ไม่มีระบบแจ้งเตือนล่วงหน้า** สำหรับรายการที่เกิดซ้ำแต่ไม่บ่อย เช่น วัคซีนประจำปี ทำให้พลาดกำหนด
4. **ครอบครัวที่มีผู้ร่วมดูแลหลายคนไม่มีข้อมูลกลางร่วมกัน** — ทำให้ไม่ทราบยอดรวมที่แท้จริง และอาจซื้อของซ้ำซ้อนกัน

**PetCostTrack** ถูกออกแบบมาเพื่อแก้ปัญหาทั้ง 4 ข้อนี้โดยตรง ด้วยการเป็นศูนย์กลางข้อมูลเดียวที่รวบรวม จัดหมวดหมู่ และคำนวณสรุปค่าใช้จ่ายให้อัตโนมัติ พร้อมระบบแจ้งเตือนและระบบแชร์สิทธิ์การเข้าถึงข้อมูลให้สมาชิกในครอบครัว

## คุณสมบัติหลักของระบบ (Key Features)

### 📊 แดชบอร์ด (Dashboard)
- สรุป KPI: ยอดใช้จ่ายรวม, ยอดค่าใช้จ่ายแฝง, % งบประมาณที่ใช้ไป, จำนวนสัตว์เลี้ยง
- กราฟวงกลม (Doughnut Chart) แสดงสัดส่วนค่าใช้จ่ายแยกตามหมวดหมู่
- รายการค่าใช้จ่ายล่าสุด
- **ตัวกรองสัตว์เลี้ยง + เดือน/ปี** เลือกดูภาพรวมของสัตว์เลี้ยงตัวใดตัวหนึ่ง หรือเดือน/ปีที่ต้องการย้อนดูได้
- **เปรียบเทียบภาพรวมค่าใช้จ่าย** กับเดือน/ปีที่ผ่านมา พร้อมตัวเลข % เปลี่ยนแปลงขึ้น/ลง

### 🐶 จัดการสัตว์เลี้ยง (Pet Profile Management)
- เพิ่ม/แก้ไข/ลบโปรไฟล์สัตว์เลี้ยง พร้อม**อัปโหลดรูปภาพ** (เก็บบน Supabase Storage)
- ระบุรายละเอียด: ชื่อ, ประเภท, สายพันธุ์ (แยกจากประเภท), เพศ, อายุ, น้ำหนัก, วันเกิด, วันที่รับเลี้ยง, หมายเลขไมโครชิป
- ฟิลด์บังคับกรอกเฉพาะ **ชื่อ, ประเภท, เพศ** ส่วนที่เหลือกรอกหรือไม่กรอกก็ได้
- แสดง badge สิทธิ์ (Owner / Co-caretaker) ของสัตว์เลี้ยงแต่ละตัว

### 💸 ประวัติรายจ่าย (Expense History)
- บันทึกรายการค่าใช้จ่าย พร้อมระบุสัตว์เลี้ยง หมวดหมู่ จำนวนเงิน วันที่ และหมายเหตุ
- แยกประเภท **ค่าใช้จ่ายหลัก** และ **ค่าใช้จ่ายแฝง** อย่างชัดเจนที่ระดับฐานข้อมูล
- ตัวกรอง: ประเภทค่าใช้จ่าย, สัตว์เลี้ยง, หมวดหมู่
- แสดงยอดรวมตามเงื่อนไขที่กรองไว้

### 💰 งบประมาณ (Budgets)
- ตั้งงบประมาณรายเดือนแยกตามสัตว์เลี้ยงแต่ละตัว
- เปรียบเทียบยอดใช้จริงกับงบที่ตั้งไว้ พร้อม progress bar เตือนเมื่อใกล้/เกินงบ
- ตัวกรองดูงบประมาณตามสัตว์เลี้ยง / เดือน / ปี

### 🔔 การแจ้งเตือน (Reminders)
- ตั้งรายการค่าใช้จ่าย/กิจกรรมที่เกิดซ้ำ (รายเดือน / รายปี) เช่น วัคซีนประจำปี ถ่ายพยาธิ
- ระบุวันครบกำหนด และทำเครื่องหมายว่าดำเนินการแล้ว
- ไฮไลต์รายการที่ถึงกำหนดหรือเลยกำหนดแล้ว

### 👨‍👩‍👧 โปรไฟล์และครอบครัว (Profile & Family)
- แก้ไขข้อมูลส่วนตัว, เปลี่ยนรหัสผ่านผ่านอีเมล
- แสดงรายชื่อสมาชิกในครอบครัวที่มีสิทธิ์เข้าถึงสัตว์เลี้ยงร่วมกัน
- แสดงจำนวนสัตว์เลี้ยงที่เป็นเจ้าของ พร้อมลิงก์ไปหน้าจัดการสัตว์เลี้ยง

### 🔐 ระบบสมาชิก (Authentication)
- สมัครสมาชิก / เข้าสู่ระบบ / ออกจากระบบ ผ่าน Supabase Auth (Email + Password)
- ผูกบัญชีผู้ใช้ใหม่เข้ากับข้อมูลตัวอย่าง (seed data) อัตโนมัติเมื่ออีเมลตรงกัน
- ป้องกันหน้าทุกหน้าไม่ให้เข้าถึงได้หากยังไม่ได้เข้าสู่ระบบ

## เทคโนโลยีที่ใช้ (Tech Stack)

| ส่วนงาน | เทคโนโลยี |
|---|---|
| **Frontend** | HTML5 + Vanilla JavaScript (ES5-style, ไม่มี framework/build step) |
| **CSS** | Tailwind CSS (โหลดผ่าน Play CDN) + `style.css` (สไตล์ที่ใช้ร่วมกันทุกหน้า เช่น dropdown, ปุ่ม, การ์ด) |
| **ไอคอน/กราฟ** | Font Awesome 6, Chart.js (กราฟวงกลมสัดส่วนค่าใช้จ่าย) |
| **ฟอนต์** | Prompt (Google Fonts) |
| **Backend / Database** | [Supabase](https://supabase.com) — PostgreSQL + Auto-generated REST API (PostgREST) |
| **Authentication** | Supabase Auth (JWT-based session, เก็บใน `localStorage`) |
| **File Storage** | Supabase Storage (bucket `pet-photos` สำหรับรูปสัตว์เลี้ยง) |
| **Deployment** | Vercel (Static Hosting พร้อม clean URL rewrites) |

> **หมายเหตุด้านสถาปัตยกรรม:** ฝั่ง Frontend เรียก Supabase โดยตรงผ่าน `fetch()` ไปยัง REST/Auth/Storage endpoint (ดูที่ `js/api.js` และ `js/auth.js`) — **ไม่ได้ใช้ Supabase JS SDK และไม่มีขั้นตอน build/bundle ใดๆ** จึงสามารถเปิดไฟล์ `.html` หรือเสิร์ฟด้วย static file server ธรรมดาได้ทันที การควบคุมสิทธิ์การเข้าถึงข้อมูลทั้งหมดทำที่ระดับฐานข้อมูลผ่าน **Row Level Security (RLS)** ไม่ใช่ที่โค้ดฝั่ง Frontend

## โครงสร้างฐานข้อมูล (Database Schema)

ออกแบบเป็นฐานข้อมูลเชิงสัมพันธ์ (Relational Database) บน PostgreSQL มีตารางหลัก 8 ตาราง:

| ตาราง | คำอธิบาย |
|---|---|
| `users` | ผู้ใช้งานระบบ (ชื่อ, อีเมล, บทบาทระดับบัญชี Owner/Co-caretaker, เชื่อมกับ Supabase Auth ผ่าน `auth_id`) |
| `pets` | โปรไฟล์สัตว์เลี้ยง (ชื่อ, ประเภท, สายพันธุ์, เพศ, น้ำหนัก, วันเกิด, วันที่รับเลี้ยง, ไมโครชิป, รูปภาพ) |
| `pet_access` | ตารางเชื่อม (Many-to-Many) ระหว่าง `users` และ `pets` — กำหนดว่าใครมีสิทธิ์อะไร (Owner/Co-caretaker) กับสัตว์เลี้ยงตัวไหน |
| `categories` | หมวดหมู่ค่าใช้จ่าย (เช่น อาหาร, วัคซีน, ค่ารักษาพยาบาลฉุกเฉิน) |
| `expenses` | รายการค่าใช้จ่าย ผูกกับสัตว์เลี้ยง ผู้บันทึก และหมวดหมู่ แยกประเภท "หลัก"/"แฝง" |
| `receipts` | ไฟล์ใบเสร็จที่แนบกับรายการค่าใช้จ่าย |
| `budgets` | งบประมาณรายเดือนของสัตว์เลี้ยงแต่ละตัว |
| `reminders` | รายการแจ้งเตือนที่เกิดซ้ำ ผูกกับสัตว์เลี้ยงและหมวดหมู่ |

รวมถึง **View** `budget_summary_view` ที่คำนวณยอดใช้จริงเทียบกับงบที่ตั้งไว้แบบ derived attribute และ **Storage bucket** `pet-photos` สำหรับเก็บรูปสัตว์เลี้ยง

### แนวคิดการควบคุมสิทธิ์
ระบบไม่ได้เก็บ "เจ้าของ" ไว้เป็นคอลัมน์ตรงๆ ในตาราง `pets` แต่ใช้ตารางเชื่อม `pet_access` (M:N) เพื่อให้สัตว์เลี้ยงหนึ่งตัวมีได้ทั้ง Owner และ Co-caretaker หลายคน และผู้ใช้หนึ่งคนดูแลสัตว์เลี้ยงได้หลายตัว การอนุญาต/ปฏิเสธการเข้าถึงข้อมูลทั้งหมด (อ่าน/เพิ่ม/แก้ไข/ลบ) บังคับใช้ที่ระดับฐานข้อมูลด้วย PostgreSQL **Row Level Security (RLS) Policies** (ดูรายละเอียดทั้งหมดในโฟลเดอร์ `supabase/migrations/`) ทำให้ต่อให้ Frontend ถูกดัดแปลง ผู้ใช้ก็ยังไม่สามารถมองเห็นหรือแก้ไขข้อมูลของสัตว์เลี้ยงที่ตนเองไม่มีสิทธิ์ได้

## สิทธิ์การใช้งาน (Roles & Permissions)

สิทธิ์ในระบบมี 2 ระดับ: **บทบาทระดับบัญชี** (`users.role`) และ **บทบาทต่อสัตว์เลี้ยงแต่ละตัว** (`pet_access.access_role`) — ผู้ใช้คนเดียวอาจเป็น Owner ของสัตว์เลี้ยงตัวหนึ่ง และเป็น Co-caretaker ของอีกตัวหนึ่งพร้อมกันได้ สรุปสิทธิ์การใช้งานจริงที่บังคับใช้ผ่าน RLS:

| การกระทำ | Owner (ของสัตว์เลี้ยงตัวนั้น) | Co-caretaker |
|---|---|---|
| ดูข้อมูลสัตว์เลี้ยง/ค่าใช้จ่าย/งบประมาณ/การแจ้งเตือน | ✅ | ✅ |

## การติดตั้งและใช้งาน (Getting Started)

โปรเจกต์นี้เป็นเว็บไซต์ static (ไม่มีขั้นตอน build) เชื่อมต่อกับฐานข้อมูล/บริการหลังบ้านผ่าน [Supabase](https://supabase.com)

### 1. เตรียมโปรเจกต์ Supabase
1. สร้างโปรเจกต์ใหม่ที่ [supabase.com](https://supabase.com)
2. เปิด **SQL Editor** แล้วรันไฟล์ในโฟลเดอร์ `supabase/migrations/` **ตามลำดับชื่อไฟล์ (เรียงตามวันที่/เวลา)** ตั้งแต่ไฟล์แรกจนถึงไฟล์ล่าสุด เพื่อสร้างตาราง, ข้อมูลตัวอย่าง (seed data), RLS Policies และ Storage bucket ให้ครบ

### 2. ตั้งค่าการเชื่อมต่อ
1. คัดลอกไฟล์ `js/config.js` เป็น `js/config.env.js` (ถ้ายังไม่มี)
2. ใส่ค่า **Project URL** และ **anon public key** ของโปรเจกต์ Supabase ของคุณ (ดูได้จาก Project Settings → API):

```js
var CONFIG = {
    SB_URL: 'https://YOUR-PROJECT.supabase.co',
    SB_KEY: 'YOUR-ANON-KEY',
    REST: 'https://YOUR-PROJECT.supabase.co/rest/v1',
    AUTH: 'https://YOUR-PROJECT.supabase.co/auth/v1'
};
```

> anon key ปลอดภัยที่จะฝังไว้ฝั่ง client เพราะสิทธิ์การเข้าถึงข้อมูลจริงถูกควบคุมด้วย Row Level Security ที่ฐานข้อมูล ไม่ใช่ตัว key เอง

### 3. รันโปรเจกต์
เนื่องจากไม่มีขั้นตอน build ใดๆ สามารถเสิร์ฟไฟล์แบบ static ได้เลย เช่น:

```bash
npx serve .
# หรือ
python3 -m http.server 5500
```

แล้วเปิดเบราว์เซอร์ไปที่ `login.html` เพื่อสมัครสมาชิก/เข้าสู่ระบบ

### 4. Deploy ขึ้น Production
โปรเจกต์ตั้งค่าให้ deploy บน [Vercel](https://vercel.com) ไว้แล้ว (ดู `vercel.json`) เพียงเชื่อมต่อ repository เข้ากับ Vercel ก็ deploy ได้ทันที (ไม่ต้องตั้งค่า Build Command เพราะเป็น static site)

## ผลสำรวจผู้ใช้และแผนพัฒนาต่อ (Roadmap)

ก่อนเริ่มพัฒนา ทีมได้เก็บข้อมูลจากแบบสัมภาษณ์ผู้เลี้ยงสัตว์จำนวน **23 คน** เพื่อยืนยันและปรับปรุง Requirement ให้ตรงกับความต้องการจริง ผลสรุปที่สำคัญ:

- เลี้ยงสัตว์ 1 ตัว 65.2% / มีผู้ร่วมดูแลค่าใช้จ่าย 87% / **73.9% ไม่เคยบันทึกค่าใช้จ่ายอย่างเป็นระบบมาก่อน**
- ฟีเจอร์ที่ผู้ใช้เห็นว่าสำคัญที่สุด (โหวตสูงสุด): **Expense Tracking**, **Pet Profile Management**, **User Authentication**
- ผู้ใช้ 82.6% เห็นว่าควรแยกโครงสร้าง "ค่าใช้จ่ายหลัก" กับ "ค่าใช้จ่ายแฝง" ที่ระดับฐานข้อมูลจริง — ระบบปัจจุบันออกแบบตามแนวทางนี้แล้ว (คอลัมน์ `expense_type`)
- ช่องทางแจ้งเตือนที่ต้องการมากที่สุดคือการผสมผสานมากกว่า 1 ช่องทาง โดยเฉพาะ **LINE Notify** และอีเมล มากกว่า Web Push Notification (มีผู้ต้องการเพียง 4.3%)

### แผนพัฒนาต่อในอนาคต

รายการต่อไปนี้ถูกระบุไว้ในเอกสาร Requirement ของโครงงาน แต่ **ยังไม่ได้พัฒนาในเวอร์ชันปัจจุบัน**:

- **ระบบเชิญ Co-caretaker ผ่านอีเมล** — ปัจจุบันการเพิ่มผู้ร่วมดูแลยังทำผ่านฐานข้อมูลโดยตรง ยังไม่มีหน้าเชิญผ่านอีเมลในตัวแอป
- **แนบไฟล์ใบเสร็จหลายไฟล์ต่อรายการ** (รองรับ jpg/png/pdf) ในหน้าเพิ่มรายจ่าย
- **แจ้งเตือนผ่าน LINE Notify / อีเมล** เมื่อถึงกำหนดรายการที่เกิดซ้ำ (ปัจจุบันมีแค่การแสดงผลในหน้า Reminders)
- **การหารค่าใช้จ่ายที่ใช้ร่วมกันหลายตัว** (Many-to-Many ระหว่าง Expense และ Pet พร้อมหารเฉลี่ยอัตโนมัติ)
- **ให้ผู้ใช้สร้างหมวดหมู่ค่าใช้จ่ายของตนเองเพิ่มเติมได้** นอกเหนือจากหมวดหมู่มาตรฐาน
- **บีบอัดรูปภาพอัตโนมัติ** เมื่อไฟล์เกิน 5MB แทนการปฏิเสธไฟล์ (ปัจจุบันระบบปฏิเสธไฟล์ที่เกินขนาดกำหนด)

รายการที่พิจารณาแล้วว่า**ไม่อยู่ในแผนพัฒนา MVP** (future feature ที่ตัดออกจาก scope):

| Future Feature | เหตุผลที่ยังไม่ทำ |
|---|---|
| AI Receipt Scanner (OCR) | ต้องใช้เวลาเทรนโมเดล AI อ่านบิลภาษาไทย เกินขอบเขตเวลาของรายวิชา |
| Connect to Vet System | ต้องรอระบบฐานข้อมูลของคลินิกเปิด API มาตรฐานก่อน |

| Pet-Friendly Location Community | เป็นฟีเจอร์เชิง Community/Location ไม่ตรงวัตถุประสงค์หลัก (Cost Tracking) |

## ข้อจำกัดที่ทราบอยู่แล้ว (Known Limitations)

- ระบบยังไม่มีการแจ้งเตือนแบบ Push/LINE/Email อัตโนมัติจริง — หน้า "การแจ้งเตือน" เป็นการแสดงรายการที่ต้องเข้ามาดูเอง
- ยังไม่รองรับการอัปโหลดใบเสร็จ (เดิมออกแบบตาราง `receipts` ไว้รองรับแล้ว แต่ยังไม่มีหน้าจอให้แนบไฟล์)
- Co-caretaker ยังไม่สามารถแก้ไขรายการค่าใช้จ่ายหรือโปรไฟล์สัตว์เลี้ยงที่ตนเองไม่ได้เป็น Owner ได้ (เข้มงวดกว่าที่เอกสาร Requirement บางข้อระบุไว้ในตอนแรก เพื่อความปลอดภัยของข้อมูล)
- ยังไม่มีหน้าจอสำหรับผู้ใช้สร้างหมวดหมู่ค่าใช้จ่ายเอง (หมวดหมู่เป็นค่าที่กำหนดไว้ล่วงหน้าในระบบ)
